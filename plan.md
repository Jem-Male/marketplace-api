# План исправлений backend

Проверка выполнена 26.09.2026. Исходный код не менялся. Команда `pytest -q`
проходит (3 теста), но покрывает только регистрацию и вход пользователя и не
обнаруживает перечисленные ниже ошибки.

## P0 — исправить прежде развёртывания

- [x] **Починить список товаров.** В `src/item/router.py:31` вызывается
  `ItemService.get_all_items(session, skip, limit)`, тогда как в
  `src/item/service.py:52` параметр `is_active` обязателен. Любой запрос
  `GET /item/items/all` завершается `TypeError` и HTTP 500. Задать в сервисе
  значение по умолчанию (например, `True`) и/или передавать значение из
  маршрута; добавить тест на этот endpoint.

- [x] **Дождаться асинхронных проверок при создании товара.** В
  `src/item/service.py:22` и `:29` вызовы DAO не имеют `await`. В переменных
  оказываются coroutine-объекты, которые всегда truthy: проверка
  существования активного пользователя и категории фактически не работает.
  Добавить `await`, проверить также магазин, категорию и пользователя на
  существование/активность и возвращать 404/403 до вставки товара.

- [x] **Исправить обработку отсутствующего товара.** В
  `src/item/service.py:69` и `:90` проверяется `item_id is None`, а не
  результат запроса `item`. При несуществующем ID следующий доступ к
  `item.creator` даёт HTTP 500. Проверять `if item is None`, возвращать 404 и
  добавить тесты update/delete для отсутствующего товара.

- [ ] **Исправить маршрут деактивации категории.** В
  `src/category/router.py:48-53` в пути указан `{category_id}`, но функция
  принимает `catrgory_id`. FastAPI воспринимает последнее как обязательный
  query-параметр, поэтому `PATCH /category/deactivate/1` отвечает 422.
  Переименовать аргумент в `category_id` и добавить интеграционный тест.

- [ ] **Закрыть административные операции авторизацией и владением.** Все
  create/update/deactivate/delete-маршруты категорий и магазинов в
  `src/category/router.py` и `src/store/router.py` доступны анонимно. В
  результате любой клиент может менять или удалять данные. Определить роли
  (минимум admin/owner), связать магазин с владельцем (`owner_id`) и проверять
  текущего пользователя через `get_current_user` в каждом изменяющем
  маршруте. Это потребует модели и новой Alembic-миграции.

- [ ] **Не отдавать секреты магазина.** `src/store/schemas.py:22-44` включает
  `ofd_token`, а публичные GET-маршруты `src/store/router.py:26-35` и
  `:57-60` не требуют токена. Разделить DTO: публичный ответ без банковских и
  кассовых секретов, приватный — только для владельца/админа. В частности,
  никогда не возвращать `ofd_token`; ограничить также доступ к реквизитам,
  если он не нужен покупателям.

- [ ] **Усилить конфигурацию JWT.** Тесты показывают предупреждение PyJWT:
  HMAC-ключ из `.env` имеет 21 байт, при SHA-256 рекомендовано не менее 32.
  В `src/user/auth.py:10-21` валидировать на старте наличие `SECRET_KEY`,
  алгоритма и положительного TTL, заменить ключ на криптографически случайный
  длиной не менее 32 байт и не добавлять `.env` в репозиторий. Добавить
  проверку конфигурации через Pydantic Settings.

## P1 — целостность данных и корректные ответы

- [ ] **Исправить проверку уникальности названия категории.** В
  `src/category/service.py:82-89` используется `if "name" in category_data`.
  Это не проверка полей Pydantic-модели, поэтому ветка обычно не исполняется;
  при дубликате будет необработанный `IntegrityError` вместо контролируемого
  409. Проверять `if "name" in update_data`, сохранить уникальный индекс БД
  и преобразовать `IntegrityError` в 409 с `session.rollback()`.

- [ ] **Обрабатывать конфликты БД и откатывать сессию во всех DAO.** Методы
  `create`, `update`, `delete` в `src/dao/base.py:48-69`, а также DAO user и
  category сразу делают `commit()`. Конфликты уникальности (например,
  `stores.bin_iin`) и внешних ключей превращаются в 500, а сессия остаётся в
  failed state. Ввести единый transaction/error handling: rollback при
  `SQLAlchemyError`, 409 для уникальных ограничений, 409/422 для нарушений FK,
  без утечки деталей БД клиенту.

- [ ] **Зафиксировать политику уникальности пользователя в БД.** В
  `alembic/versions/791a637f0afa_update_user_tables.py:27` удаляется unique
  индекс email; `src/user/model.py:22-23` не задаёт unique и для телефона.
  Проверки в сервисе касаются только активных пользователей и не защищают от
  конкурентных запросов. Если email/телефон должны быть уникальны всегда —
  добавить unique constraints. Если допускается повторное использование после
  деактивации — добавить PostgreSQL partial unique indexes для активных
  записей на оба поля. Покрыть гонку/дубликаты тестами.

- [ ] **Не позволять клиенту менять системные поля.**
  `src/item/schemas.py:55-64` требует `updated_at` в теле обновления, хотя это
  поле должно выставляться сервером; его следует убрать из request-схемы.
  В `UserUpdateRequest`, `CategoryUpdateRequest` и `StoreUpdateRequest`
  пересмотреть `is_active`: сейчас его можно прислать в обычном update, в
  обход отдельных endpoints деактивации. Оставить статус только в защищённых
  сервисных операциях.

- [ ] **Согласовать схему создания товара с моделью.** В
  `src/item/schemas.py:21-29` поле `store` допускает `None`, а
  `src/item/model.py:30` и миграция требуют non-null. Сделать `store`
  обязательным в create-схеме. Определить, допустима ли категория `None`; если
  нет — также сделать её обязательной. Валидировать, что создатель вправе
  добавлять товар именно в указанный магазин.

- [ ] **Исправить пагинацию.** В сервисах category/store/item условие
  `limit < skip` (`src/category/service.py:20`, `src/store/service.py:28`,
  `src/item/service.py:56`) ошибочно: offset 200 и limit 100 — валидный
  запрос. Проверять `skip >= 0`, `limit > 0` и установить максимальный limit.
  Аналогично запретить `limit=0` в user-сервисе (`src/user/service.py:64`).

- [ ] **Возвращать корректный HTTP-статус и контракт ответа.** Методы поиска
  user/category/store используют 400 при отсутствии ресурса (например,
  `src/user/service.py:73`, `src/category/service.py:43`,
  `src/store/service.py:55`); заменить на 404. Добавить `response_model` для
  всех list-endpoints и выделить отдельные list/detail schemas. Сейчас
  `GET /item/items/all` объявлен как `List[ItemBaseSchema]`, хотя base-схема
  не содержит `id`, `created_at`, `updated_at` и не описывает контракт списка.

## P2 — миграции, конфигурация и тесты

- [ ] **Создать новую Alembic-миграцию и сверить её с моделями.** Миграция
  `alembic/versions/c68b5ae57012_create_item_table.py` не содержит
  `check_stock_positive`, хотя ограничение объявлено в
  `src/item/model.py:43`. Добавить DB constraint `stock >= 0` новой миграцией
  (не переписывать уже применённую), затем проверить `alembic upgrade head` на
  чистой PostgreSQL базе. Заодно задать server defaults для `is_active`, если
  эти поля могут вставляться вне ORM.

- [ ] **Сделать настройки явными и безопасными.** В `src/config.py` и
  `src/database.py:15-27` отсутствует валидация обязательных DB-переменных, а
  `echo=True` пишет SQL и параметры в логи. Перенести настройки в
  `BaseSettings`, отключить echo по умолчанию, включать его только локальным
  флагом и настроить безопасное логирование.

- [ ] **Расширить тесты.** Сейчас есть только `test/test_user.py`; добавить
  tests для category, store и item: все CRUD-сценарии, 401/403, 404, дубликаты,
  невалидную пагинацию, деактивацию и foreign keys. Проверять response schema,
  отсутствие `ofd_token` в публичных ответах и отсутствие HTTP 500 на
  ожидаемых ошибках. Убрать неиспользуемые импорты и отладочный вывод из
  `test/conftest.py` и `test/test_user.py`.
